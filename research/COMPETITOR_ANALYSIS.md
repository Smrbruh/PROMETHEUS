# PROMETHEUS Phase 0 — competitor and technology analysis

Review date: **2026-10-10**. Status: **primary-document review, not hands-on product testing**. Sources describe capabilities; no product was installed, benchmarked, purchased, or connected to a customer account. Commercial claims of acceleration or accuracy are not adopted as independent evidence. “Unverified” means not established by the accessed material, not unavailable. Current unversioned pages and repository branches are snapshots, not permanent release guarantees.

## Decision

Use **Python for research orchestration, a transparent CPU finite-element baseline, and a separately implemented verification solver**. Commercial tools are useful capability comparators and optional later checks. They should not be mandatory dependencies on a personal computer.

Established products already cover most of the broad PROMETHEUS vision: constrained topology and shape optimization, manufacturing controls, scripting, response trade-offs, surrogate integration, uncertainty features and simulation orchestration. The defensible research opportunity must be an experimentally distinguishable method with an explicit cost/accuracy benefit. A new collection of these capabilities is not enough.

FreeCAD is valuable for CAD interoperability and inspection, but including its GUI in every optimization iteration would create unnecessary coupling. A text-based CalculiX verification adapter can be independent of the optimizer's assembly code. Solver agreement remains numerical verification, not physical validation: both solvers can share the same wrong material model or boundary condition.

DTU's software catalogue includes more codes than inspected here. License status must be checked for each exact file. Use published equations with attribution for an independently written implementation, or obtain clear reuse terms before copying code. Reproducing the algorithm is scientifically necessary; copying an ambiguously licensed implementation is not.

## Language and architecture choice

**Python first** is an engineering recommendation inferred from the accessible libraries and small initial problem, not a benchmark result. Keep geometry/design, FE assembly, optimizer, verification and reporting behind typed data contracts. Use immutable units-aware input records and content-addressed run directories. A minimal result should include residual, reactions, energy/compliance, displacement, solver status and provenance; unsuccessful analyses must not become attractive objective values.

**C++ later** is appropriate for measured assembly, filtering or geometry bottlenecks. Existing compiled numerical/CAD libraries already perform much heavy work. Rewriting validated kernels before profiling raises verification cost without evidence of benefit.

**Rust is not selected for the numerical core** at this stage. Memory safety may help a future service or robust tooling layer, but this review did not establish a Rust FE/topology stack with lower integration and validation cost than the inspected Python/C++ ecosystem. This is a project-specific choice, not a claim that Rust cannot implement mechanics.

Separate optimizer and verifier beyond merely two function names: use different assembly/solver implementations, independently generated meshes where feasible, and final binary/manufacturable geometry. Export and cleanup can alter volume, stiffness and stress; check the exported artifact.

## What to reuse, what to test, what not to claim

- **Reuse mature functionality:** sparse linear algebra, CAD kernels, mesh generation, FE assembly infrastructure, conventional SIMP/OC, Pareto search and Bayesian-acquisition implementations.
- **Test the proposed research contribution:** a precise adaptive scenario-selection, verification or discrepancy-learning mechanism under fixed total computational budgets, against strong conventional methods.
- **Do not claim novelty:** automatic bracket generation, weighted objectives, robustness, surrogate optimization, headless CAD/CAE orchestration, or AI-assisted requirement entry in isolation.
- **Do not claim superiority from this matrix:** no equal-budget head-to-head product experiment or independent physical validation was performed.
- **Do not infer absence:** undocumented feature combinations, commercial API access and proprietary uncertainty methods remain open questions.

The practical comparison baseline should be a published, independently reproducible algorithm plus a separate solver check. Optional commercial comparisons become useful only when version, settings, access terms and equivalent objective/constraint definitions can be disclosed. Broad “better than generative design” language is not supported by this investigation.
